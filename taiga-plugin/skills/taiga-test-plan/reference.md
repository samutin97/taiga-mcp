# Тест-план: методология

Кейс в Taiga — задача под историей, а не отдельная сущность: трекер её не
знает, и заводить кастомное поле или отдельный список смысла нет. Связь
«история — задачи» уже есть из коробки, ссылка на кейс видна сама собой, а в
отчёте по спринту проверки идут как обычная работа, а не отдельный
параллельный учёт. Источник подхода — обсуждение сообщества Taiga, где
тест-кейсы ведут как задачи под историей, а не заводят под них отдельную
сущность.

Дефект — issue, а не задача: он живёт своей жизнью после того, как кейс,
который его нашёл, уже закрыт, и должен быть виден в общем потоке багов, а
не потеряться внутри конкретной истории.

## Именование

`Subject` кейса начинается с «Проверить: …» и продолжается тем, что именно
проверяется, а не порядковым номером и не словом «тест» без подробностей.
Так: «Проверить: сброс пароля с истёкшей ссылкой». Не так: «Тест-кейс 3»
или «Тестирование функционала сброса пароля».

## Структура кейса — прозой, без рубрик

Предусловие, шаги и ожидаемый результат идут в `description` обычным текстом,
без заголовков «Шаги:», «Предусловие:», «Ожидаемый результат:» над ними —
то же правило, что для описаний историй в `taiga-voice`, здесь действует
так же.

Пример:

```
Пользователь на странице входа, ссылка для сброса пароля получена вчера и
ни разу не использовалась. Переходит по ней через 25 часов после отправки.
Ссылка недействительна, форма сброса не открывается, есть предложение
запросить письмо заново.
```

Последнее предложение и есть ожидаемый результат — читатель не должен
угадывать, где заканчивается сценарий и начинается ожидание.

## Definition of Ready для тестирования

Прежде чем брать историю на проверку, смотри:

- задачи разработки по истории закрыты
- критерии приёмки в истории сформулированы и проверяемы
- нет открытых блокировок
- изменения развёрнуты на тестовом стенде
- тестовые данные подготовлены
- известен человек, который проверяет

Истории, которая не проходит хотя бы один пункт, статус «готова к тесту»
не присваивается — скажи, чего именно не хватает, а не переводи статус
на будущее обещание.

## Definition of Done

Все кейсы под историей закрыты; найденные дефекты либо исправлены, либо
владелец истории явно согласился перенести их на следующий релиз. Перенос
без согласия владельца — это не Definition of Done, а его имитация: список
кейсов закрыт, а проблема осталась не решённой и не зафиксированной.

## Severity и priority дефекта

Severity — что происходит с пользователем: падает ли функциональность целиком,
есть ли обходной путь, заметна ли проблема вообще без специального сценария.
Priority — когда чинить: дефект с высоким severity может подождать релиза,
если задевает редкий сценарий, а дефект с низким severity — уйти в текущий
спринт, если ломает демонстрацию клиенту завтра. Значения назначаются
раздельно, одно не выводится из другого автоматически.

## Регресс

Кейс, который имеет смысл повторять при каждом релизе, а не один раз ради
конкретной истории, помечается тегом `regression`. Так регрессионный набор
собирается фильтром по тегу, а не пересобирается заново каждый раз вручную.
