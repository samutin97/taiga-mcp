# Переходы по этапам и готовность

Какой сущностью оформить работу, роли, поинты и модель блокировок — в `taiga-model`;
форма критериев и открытых вопросов — в `taiga-requirements`. Этот скилл — про третье:
как запись движется по статусам, когда предложить следующий шаг и что снять при
закрытии. Граница с `taiga-worklog`: ворклог — повседневная запись хода работы над
своей задачей (нашёл её, отметил прогресс комментарием, поставил блокировку); этот
скилл — про переходы истории и задачи между этапами целиком, готовность истории к
спринту и снятие блокировок при закрытии. Меняю статус одной задачи по ходу кодирования
— это `taiga-worklog`; решаю, что из этого следует для всей истории, или проверяю,
можно ли историю брать в спринт или закрывать, — это здесь.

## Статусы беру только из проекта

Стандартный набор Taiga: у истории New → Ready → In progress → Ready for test → Done,
у задачи New → In progress → Ready for test → Closed. Имя статуса не подставляю
наизусть — читаю `taiga_project_schema`, `lookups["userstory-status"]` и
`lookups["task-status"]`: это массивы в порядке колонок доски, первый элемент — начало
работы, последний — закрытие. Названия проекта совпадают со стандартными — использую
их как есть. Не совпадают — сопоставляю по смыслу и позиции (первый элемент = «New»,
последний = «Done»/«Closed», средние — по близости названия к стандартному шагу) и
прямо называю пользователю, какое сопоставление применил, раньше первого вызова
`_update`.

## Готовность истории к спринту

Проверяю одну историю за раз, ничего не поправляю сам — только показываю, что нашёл, и
чего не хватает.

- [ ] `taiga_userstory_get ref=<N> fields="full"` — в `description` есть рубрика
      `## Критерии приёмки`, и она не пустая.
- [ ] в том же `description` рубрика `## Открытые вопросы` пустая или отсутствует —
      открытый вопрос без ответа живёт в требованиях (`taiga-requirements`), не в
      комментариях: комментарии — для прогресса, не для непринятых решений.
- [ ] `taiga_task_list user_story=<N>` — задачи есть, и у каждой в `tags` стоит роль
      (`front`/`back`/`ux`/`design`).
- [ ] в том же ответе `taiga_userstory_get ... fields="full"` поле `points_by_role` несёт
      число по каждой роли, чьи задачи нашлись на шаге выше, и ни одно не больше 40.
      Сырое поле `points` рядом — это карта внутренних идентификаторов, не разбивка;
      читаю только `points_by_role`. Оценок у задач нет и быть не должно: вес работы
      живёт у истории (`taiga-model`).
- [ ] в том же `taiga_userstory_get ... fields="full"` поле `blocked_by` пустое.

Сошлось всё — говорю «готова к спринту», перечисляя, что проверил. Не сошлось хоть
одно — называю именно недостающее и не предлагаю брать историю в спринт.

## Переходы истории

- Первая задача истории переходит в статус, сопоставленный с «In progress», —
  предлагаю перевести и саму историю: `taiga_userstory_update ref=<N> status="<имя из
  схемы>"`.
- `taiga_task_list user_story=<N> is_closed=false` возвращает пустой список — все
  задачи истории дошли до статуса, сопоставленного с «Closed», — предлагаю историю в
  её «Ready for test».
- Пользователь подтвердил, что проверка (тест) прошла, — предлагаю «Done».

Каждый раз это предложение с явным ожиданием «да»: называю `#ref`, текущий статус,
предлагаемый новый — и не вызываю `_update`, пока не услышал согласие. Расхождение
(например, просят Done, а задачи ещё открыты) — говорю прямо и не подставляю статус,
который не подтверждён состоянием задач.

## Переходы задачи

Статус конкретной задачи по ходу работы меняет `taiga-worklog` — здесь этот вызов не
дублирую. Мне интересно следствие для истории целиком: увидел смену статуса задачи —
смотрю, какой из переходов истории выше это открывает, и предлагаю его.

## Закрытие и снятие блокировок

Перед статусом, сопоставленным с «Closed»/«Done»: сначала смотрю в
`taiga_project_schema`, есть ли у типа закрываемой записи (`customFields.task`
или `customFields.userstory`) поле «Блокирует» — без него `blocks` всегда
пустой независимо от реальных блокировок. Поля нет — прямо говорю, что не вижу,
что блокирует эта запись, и предлагаю проверить руками (спросить в команде,
посмотреть похожие записи по смыслу), а не докладываю «всё чисто». Поле есть —
смотрю `blocks` из `taiga_task_get`/`taiga_userstory_get` с `fields="full"` для
закрываемой записи. Список пуст — закрываю без дополнительных вопросов. Не пуст — называю каждую
заблокированную запись (`#ref`, заголовок) и предлагаю снять блокировку по ней:
`taiga_link from=<ref закрываемой> to=<ref заблокированной> type="blocks" remove=true`.
Снимаю только по тем позициям, с которыми согласился пользователь; часть списка можно
оставить как есть, если так решили явно — я не снимаю блокировку вместо человека. Снимаю
блокировку только этим вызовом, а не правкой `is_blocked`/`blocked_note` через `_update`
руками: так флаг гаснет только тут, а «Блокирует» на другой стороне и запись
«Разблокировал» не появляются.

## Что мешает закрыть

Собираю и называю всё сразу, а не по одному вопросу: `is_blocked`/`blocked_note` у
самой записи, незакрытые задачи истории (`taiga_task_list user_story=<N>
is_closed=false`), непустая рубрика `## Открытые вопросы` в описании. Пока хоть одно из
этого не снято, не предлагаю статус закрытия — говорю, что именно держит запись
открытой.

## Границы

Ни один вызов `_update` не уходит по одной лишь моей догадке о готовности — только
после явного согласия на конкретный переход. Не снимаю блокировку с записи, которую
пользователь не назвал отдельно. Не подставляю статус, которого нет в
`taiga_project_schema` этого проекта.
