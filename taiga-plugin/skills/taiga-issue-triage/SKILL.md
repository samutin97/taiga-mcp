# Триаж issue в Taiga

## Что разбирать

`taiga_issue_list` без фильтров даёт весь поток. Срез `slim` по умолчанию уже
содержит `priority`, `severity`, `type` и `status` — отдельные вызовы не нужны.
Неразобранное обычно то, где статус начальный, а исполнителя нет
(`assigned_to` пуст).

## Допустимые значения

Приоритеты, severity и типы у каждого проекта свои. Посмотри их один раз
через `taiga_project_schema` и держись этого списка. Если передашь имя,
которого нет, инструмент вернёт ошибку с перечнем допустимых значений —
это подсказка для повторной попытки, а не сбой, который нужно эскалировать.

## Разбор одного issue

`taiga_issue_update` принимает `priority`, `severity`, `type`, `assigned_to`
и `status` человеческими именами, например: приоритет "High", severity
"Important", тип "Bug", исполнитель "Иван Петров" — всё в одном вызове
`taiga_issue_update` по нужному `ref`.

Прежде чем назначать человека, убедись, что он в проекте — список участников
есть в `taiga_project_schema`.

Снять исполнителя — `assigned_to: ""` (пустая строка); так же убирается срок
(`due_date: ""`). Это единственный способ очистить поле: `null` схема
не принимает. Возвращая issue в общую очередь, скажи об этом пользователю.

## Дубли

Перед тем как заводить новый issue, прогони `taiga_search` по ключевым словам.
Нашёл похожий — добавь комментарий через `taiga_comment_add` (`resource: "issue"`)
вместо создания второго.

## Границы

Приоритет и severity — решение пользователя, а не твоё. Предлагай значения
с обоснованием и меняй после согласия. Массовую переразметку показывай списком
до применения. `taiga_issue_delete` требует `confirm: true` и явного согласия
пользователя; закрытие статусом почти всегда лучше удаления.
