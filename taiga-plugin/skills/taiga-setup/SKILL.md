# Подключение к Taiga

## Проверка

Начни с `taiga_whoami`. Успешный ответ даёт имя пользователя и список проектов
с их слагами — этого достаточно, чтобы понять, что связь есть.

## Настройка

Три источника, в порядке предпочтения:

1. `/plugin` → taiga → настройки — адрес инстанса, логин, пароль, проект по
   умолчанию. Основной путь для пользователя с UI.
2. Переменные окружения, если `/plugin` недоступен: `TAIGA_URL`, `TAIGA_USERNAME`,
   `TAIGA_PASSWORD`, необязательная `TAIGA_PROJECT`.
3. Файл `config.json` в каталоге данных плагина (`CLAUDE_PLUGIN_DATA`) — последний
   вариант, когда ни первое, ни второе не подходит:

   ```json
   {
     "url": "https://taiga.example.com",
     "username": "...",
     "password": "...",
     "project": "my-project"
   }
   ```

   Файл создаёт сам пользователь. Твоё дело — показать этот формат и путь к
   каталогу, не писать файл за него.

`TAIGA_URL`/`url` — адрес инстанса без `/api/v1`. `TAIGA_PROJECT`/`project` задаёт
проект по умолчанию (id или slug), чтобы не указывать его в каждом вызове; слаг
можно взять из вывода `taiga_whoami`.

Технически настройки из `/plugin` тоже попадают в процесс через переменные
окружения — сервер сначала читает обычные `TAIGA_URL`/`TAIGA_USERNAME`/
`TAIGA_PASSWORD`/`TAIGA_PROJECT` и только потом то, что подставил `/plugin`.
Если значение выглядит устаревшим после смены настроек в UI — проверь, не
задана ли одноимённая переменная прямо в оболочке: она победит.

## Разбор ошибок

| Что видно | Что это значит |
|---|---|
| `The Taiga plugin is not configured: … are not set` | Ни один из трёх источников не дал значение для одного или нескольких полей. |
| `Cannot reach Taiga at …` | Неверный адрес инстанса или инстанс не поднят. Проверь адрес в браузере. |
| `Taiga rejected the login for user "…"` | Неверные логин или пароль. |
| `No Taiga project specified` | Не задан проект по умолчанию и не передан параметр `project`. |
| `not enough permissions` | Учётной записи не хватает роли в проекте. |

Никогда не проси пользователя прислать пароль в чат и не выводи его сам, даже
при пересказе этой таблицы, содержимого переменных окружения или `config.json`.

## Что доступно в проекте

`taiga_project_schema` показывает допустимые статусы, приоритеты, severity,
типы issue, оценки, роли и участников. Он нужен, чтобы показать пользователю
варианты, — но не перед записью: имена статусов и людей резолвятся автоматически,
а при ошибке инструмент сам вернёт список допустимых значений.

## Как настроить проект под стадию

До релиза, пока основной поток — новая функциональность: Scrum, спринты по две
недели, истории оценены в поинтах до начала спринта — здесь помогает
`taiga-estimate`. После релиза, когда основной поток — issue от пользователей:
Kanban с лимитом WIP, issue как основной вход — здесь помогает `taiga-issue-triage`.

Честно: сам плагин не переключает модули проекта (бэклог/канбан/issues/wiki) —
это делается в настройках проекта в веб-интерфейсе Taiga, инструментами не
управляется.

Статусы под Definition of Ready / Definition of Done — рекомендация, а не
готовое решение: «Новая → Готова к разработке → В работе → Готова к тесту →
Закрыта». Заводятся и переименовываются статусы тоже в UI Taiga.

## Поля проекта

Ролям, оценкам, блокировкам и связям в карточках нужны четыре кастомных
атрибута — плагин их не заводит:

| Атрибут | Тип | На чём | Для чего |
|---|---|---|---|
| «Оценка» | число | задачи | оценка задачи в поинтах — без неё нет ни `estimate`, ни поинтов истории по роли |
| «Блокируется» | текст | задачи, истории | витрина блокировки в карточке; источник истины всё равно флаг `is_blocked` и примечание |
| «Блокирует» | текст | задачи, истории | обратная сторона той же витрины |
| «Связано с» | текст | задачи, истории | список простых связей — в отличие от блокировки, у «просто связаны» другого носителя нет |

Заводит их администратор проекта в самой Taiga: Admin → Attributes →
Custom fields, отдельно для задач и для историй.

`taiga_project_schema` показывает эти четыре поля прямо: в `customFields.task`
и `customFields.userstory` лежат списки `{name, type}` по кастомным атрибутам
задач и историй соответственно. Есть ли «Оценка» — смотри, входит ли в
`customFields.task` запись `{name: "Оценка", type: "number"}`; так же
проверяются «Блокируется», «Блокирует» и «Связано с» по обоим спискам —
у задач и у историй, как в таблице выше. Для поинтов по роли важно ещё
одно поле схемы: `lookups.role` должен содержать роли `Front`/`Back`/`UX`/
`Design` (без учёта регистра) — иначе оценка задачи запишется, а поинты
истории не пересчитаются.

Если ответ схемы почему-то не получить — годятся и косвенные признаки:
`taiga_stats` со `sprint` вернёт `load: []` и `load_note`, если «Оценки»
в проекте нет вовсе; запись `estimate` без поля даст ошибку с его именем,
а `taiga_link` с `type: "relates"` без «Связано с» вернёт `hint` вместо
связи.

Без «Оценки» — нет оценки задачи и поинтов истории по роли, `taiga_stats`
не считает загрузку. Без «Блокируется»/«Блокирует» блокировка всё равно
работает: флаг и примечание пишутся без атрибута, в карточке просто не
появится витрина. Без «Связано с» `taiga_link` с `type: "relates"` связь
не запишет вообще — ни флага, ни примечания у простой связи нет, атрибут
здесь единственный носитель.

## Режимы

`TAIGA_READ_ONLY=1` — регистрирует только 21 инструмент, ни один не меняет
Taiga. Включай для отчётных сессий, где запись не нужна и не должна случиться
по ошибке.

`TAIGA_VOICE_GUARD=warn` или `=block` — серверная проверка исходящих текстов,
не зависящая от хуков клиента; предложи её, если хуки в конкретном клиенте
недоступны. `warn` дописывает находки в ответ инструмента, `block` отклоняет
вызов с ошибкой — тогда текст нужно переписать и отправить заново.
