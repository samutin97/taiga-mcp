# Приоритизация бэклога: методы

Четыре способа упорядочить бэклог — от самого грубого до самого точного.
Для каждого: что это, формула (если есть), когда применять и когда не стоит.

## MoSCoW

Грубая сортировка по обязательности, а не по числу.

- Must have — без этого релиз не имеет смысла или сорвано обязательство перед кем-то снаружи.
- Should have — важно, но есть обходной путь, можно пережить без этого один релиз.
- Could have — заметно, но не критично; первое, что снимают при нехватке времени.
- Won't have (this time) — сознательно не сейчас, а не «никогда»; список тоже стоит вести, чтобы не спорить о том же через месяц.

Правило: must ≤ 60 % усилий спринта. Если must занимает больше — это не приоритизация,
а переименованный список всего бэклога, и первое обещание, которое команда не выполнит,
будет как раз в этой группе.

Хорошо подходит для большого бэклога — от нескольких десятков историй — и для первого
грубого прохода перед более точным методом. Если бэклог уже небольшой и прошёл первый
отсев, MoSCoW не поможет: он не различает порядок внутри одной группы, там нужна матрица
или RICE.

## Матрица влияние/усилия

Две оси — влияние (польза для пользователей или бизнеса) и усилие (стоимость реализации).
Четыре квадранта:

- высокое влияние / низкое усилие — быстрые победы, делать первыми;
- высокое влияние / высокое усилие — крупные ставки, планировать и резать на этапы;
- низкое влияние / низкое усилие — мелочь по остаточному принципу, если останется время;
- низкое влияние / высокое усилие — не делать.

Хорошо работает на 10–30 историях, в разговоре с командой вживую, где важно быстрое общее
согласие, а не точное число для отчёта. При большем числе историй матрица перестаёт
работать на глаз и обсуждение расползается; если нужен письменный порядок для людей
снаружи команды, лучше взять RICE или WSJF.

## RICE

```
score = reach × impact × confidence / effort
```

- reach — сколько пользователей или событий за выбранный период (например, за квартал).
- impact — эффект на одного пользователя из ряда: 3 огромное, 2 большое, 1 среднее,
  0,5 малое, 0,25 минимальное.
- confidence — насколько надёжны цифры reach и impact: 100 % — есть данные,
  80 % — обоснованная оценка, 50 % — догадка.
- effort — трудоёмкость в человеко-неделях или поинтах команды.

Пример. Чат-бот в поддержке: reach 4000, impact 2 (большое), confidence 100 %, effort 1:

```
4000 × 2 × 1,00 / 1 = 8000
```

Платёжный шлюз: reach 1500, impact 3 (огромное), confidence 75 %, effort 1:

```
1500 × 3 × 0,75 / 1 = 3375
```

Чат-бот выше платёжного шлюза, хотя влияние на одного пользователя у шлюза больше:
он просто затрагивает меньше людей и оценка по нему менее надёжна.

Хорошо подходит, когда нужен обоснованный порядок для стейкхолдеров и по reach есть хоть
какие-то данные — аналитика, воронка, а в бэклоге много разноразмерных фич. Если reach для
всех пунктов берётся на глаз и одинаково, RICE только создаёт видимость точности там, где
её нет; для эпиков с дедлайнами лучше подходит WSJF.

## WSJF

```
cost of delay = user value + time criticality + risk reduction/opportunity
wsjf = cost of delay / duration
```

Каждая из трёх составляющих cost of delay — по шкале 1–10.

Пример. Эпик «онбординг новых клиентов»: user value 8, time criticality 5,
risk reduction 3, duration 2:

```
(8 + 5 + 3) / 2 = 8
```

Эпик «миграция биллинга»: user value 5, time criticality 8, risk reduction 2, duration 5:

```
(5 + 8 + 2) / 5 = 3
```

Онбординг идёт первым: та же цена задержки набегает у него быстрее в пересчёте на срок
реализации.

Хорошо подходит для эпиков и портфеля на уровне квартала, когда есть дедлайны или окна
возможностей. Плохо подходит для отдельных историй внутри одного эпика — гранулярность
слишком крупная; и не работает, если команда не договорилась об одной шкале для user value
и risk reduction, — тогда цифры разных людей несравнимы между собой.

## Антипаттерны

- Приоритет по громкости заказчика — кто последним написал или громче настоял,
  тот и в начале очереди.
- Всё в must — обязательность без исключений не сортирует, а просто откладывает выбор.
- Числа RICE или WSJF, записанные в Taiga как поле, а не как разговор, — устаревают
  при первом изменении контекста и выглядят так, будто их никто не пересматривал.
- Переприоритизация каждый день — команда не успевает довести до конца даже быстрые
  победы, если верхушка очереди меняется чаще, чем раз в спринт.
