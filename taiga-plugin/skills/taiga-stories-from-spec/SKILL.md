# Из текста в бэклог Taiga

## История = ценность, задача = техника

История — проверяемый результат для пользователя, а не пересказ абзаца
исходника. Задача — техническая часть работы внутри истории. Раскладывай
материал на истории по умолчанию; задачи заводи вторым проходом только
если пользователь явно просит разбивку до задач или материал сам по себе
технический (миграция, инфраструктура, рефакторинг без видимого результата
для пользователя) — иначе оставь разбивку на задачи планированию спринта.

## Порядок

1. **Разбери текст.** Выдели самостоятельные единицы работы. Одна история —
   один проверяемый результат, а не один абзац исходника.
2. **Проверь на готовность** (Definition of Ready, как в `taiga-backlog-grooming`). По каждой будущей истории: польза понятна,
   критерии проверяемы, зависимости названы. История, которая не проходит
   это — либо дробится, либо остаётся вопросом к пользователю, а не
   черновиком с додуманными критериями.
3. **Покажи план.** Выведи черновик каждого элемента целиком — заголовок и
   описание, не только заголовки списком — и дождись согласия. Это
   обязательный шаг: создание двадцати историй по неверно понятому документу
   дороже, чем один уточняющий вопрос.
4. **Создай.** `taiga_bulk_create` с `resource: "userstory"`, до пятидесяти
   элементов за вызов.
5. **Разбери результат.** Инструмент возвращает `created` и `failed`.
   Разбери причины неудач и повтори запрос только с ними — не создавай всё заново.

## Формат элементов

Каждый элемент принимает те же поля, что `taiga_userstory_create`. Заголовок —
формулировка результата, а не техническое задание; описание — польза первой
фразой и критерии обычными строками, без рубрики над ними:

```json
{
  "subject": "Сброс пароля по email работает без поддержки",
  "description": "Чтобы поддержка перестала сбрасывать пароли руками.\n\nПисьмо приходит в течение минуты, ссылка живёт сутки, после смены старые сессии закрыты.",
  "tags": ["auth"]
}
```

Статусы, исполнителей, оценки (`points: "5"`) и спринт (`sprint: "<название>"`)
указывай человеческими именами — резолв в числовые ID происходит сам, ровно как
в `taiga_userstory_create`. Поля `points` и `sprint` есть только у user stories;
в элементе `resource: "task"`/`"issue"` такой элемент вернётся в `failed`
с понятной причиной, а не будет создан молча без них.

## Задачи под историями

Заводи задачи только по условию из раздела выше. Когда заводишь — вторым
проходом, после того как истории получили номера: `taiga_bulk_create` с
`resource: "task"`, где `user_story` — номер `#ref` созданной истории из
ответа первого вызова.

## Discovery

Исследование, прототип, дизайн-макет — это тоже история, а не задача: у неё
есть проверяемый результат (вопрос закрыт, макет готов к реализации), просто
не пользовательский. Заводи её обычной историей с тегом `discovery`, чтобы
она была видна в бэклоге отдельно от фич.

## Артефакты дизайна

Макет, скриншот, файл — вложением через `taiga_attachment_upload`, не
пересказом в тексте описания и не ссылкой на внешний файл, которого не будет
через полгода. `taiga_attachment_upload` требует подтверждения — спрашивай
пользователя перед загрузкой и дожидайся согласия.

## Эпики

Если материал явно делится на крупные направления, можно предложить завести
эпики через `taiga_epic_create` — но не по своей инициативе, спроси.
Привязывай истории к эпику полем `epic` — оно работает и в
`taiga_bulk_create`: добавь `"epic": "<название эпика>"` в элемент, и
история будет создана уже привязанной к нему, без отдельного прохода
`taiga_userstory_update` после пакетной заливки. Поле `epic` в элементах
`resource: "task"`/`"issue"` не имеет смысла — такой элемент вернётся
в `failed` с понятной причиной.

## Чего не делать

Не выдумывай критерии приёмки, которых нет в источнике. Если раздел документа
слишком расплывчат, чтобы стать историей, скажи об этом, а не сочиняй.
