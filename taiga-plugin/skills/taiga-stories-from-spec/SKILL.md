# Из источника в бэклог Taiga

## Откуда берёшь вход

Источник — документ (спека, заметки со встречи, переписка, обсуждение) или уже
заведённая в Taiga сущность, которую просят разложить дальше:

- **Документ.** Начинай с разбора текста; эпики предлагай по обстоятельствам
  (раздел «Эпики»), затем истории, затем — по условию ниже — задачи.
- **Существующий эпик** (`#ref` или название). Прочитай `taiga_epic_get`: цель,
  границы и критерий готовности — рубрики `## Цель`, `## Границы`,
  `## Готово, когда` в его описании (`taiga-requirements`). `taiga_userstory_list`
  с фильтром `epic` покажет истории, которые уже заведены — не предлагай их
  заново. Сам эпик не пересоздавай, раскладывай его на истории.
- **Существующая история** (`#ref`). Прочитай `taiga_userstory_get`: описание
  и критерии приёмки — источник для задач. Историю и эпик не трогай,
  раскладывай прямо на задачи (раздел «Задачи под историями»).

Дальше правила общие независимо от того, что было источником.

## История — слайс ценности, не слой

История — вертикальный, проверяемый результат для пользователя, а не пересказ
абзаца исходника и не технический слой отдельной строкой («бэкенд для фичи
X»). Бековая работа по умолчанию — задачи внутри той же истории, что и фронт:
одна польза, один план. Отдельную техническую историю предлагай и спрашивай
подтверждения только когда подходит один из трёх случаев `taiga-model` (API
нужен нескольким историям, работу делает другая команда, это инфраструктура
без прямой пользы пользователю) — никогда не заводи её по своей инициативе.

Раскладывай материал на истории по умолчанию; задачи заводи вторым проходом,
когда пользователь явно просит разбивку до задач, материал сам по себе
технический (миграция, инфраструктура, рефакторинг без видимого результата
для пользователя) или источник — сама история, которую просят разложить
(тогда это и есть весь запрос).

## Порядок работы

1. **Разбери источник.** Из документа выдели самостоятельные единицы работы;
   из эпика — направления, которые тянут на отдельную историю; из истории —
   шаги плана, которые тянут на задачу. Одна история — один проверяемый
   результат, а не один абзац или один компонент экрана.
2. **Проверь на готовность** (Definition of Ready, как в
   `taiga-backlog-grooming`): польза понятна, критерии проверяемы, зависимости
   названы. История, которая не проходит это — либо дробится, либо остаётся
   вопросом к пользователю, а не черновиком с додуманными критериями.
3. **Запиши по рубрикам `taiga-requirements`.** История — `## Описание` и
   `## Критерии приёмки`, по месту `## Открытые вопросы`; эпик — `## Цель`,
   `## Границы`, `## Готово, когда`; задача — `## Что сделать`,
   `## Как проверить` (у бековой ещё рубрика — раздел «Задачи под
   историями»). Форму критерия — правило, EARS, таблица решений, Gherkin —
   выбирай по решётке `taiga-requirements`, не списком по умолчанию.
4. **Покажи план и дождись согласия.** Черновик каждого элемента целиком —
   заголовок и описание со всеми рубриками, не только заголовки списком.
   Создание двадцати историй по неверно понятому документу дороже одного
   уточняющего вопроса; ничего не создавай до явного «да».
5. **Создавай по порядку: эпики → истории → задачи → связи.** За один вызов
   `taiga_bulk_create` — не больше пятидесяти элементов; крупную
   декомпозицию разбивай на несколько вызовов. Эпики — только если материал
   их оправдывает (раздел «Эпики»), первыми. Истории — `taiga_bulk_create` с
   `resource: "userstory"`, при необходимости сразу с полем `epic`. Задачи —
   второй вызов `taiga_bulk_create` с `resource: "task"`, `user_story` —
   номер `#ref` уже созданной истории, у каждой — `role`
   (раздел «Задачи под историями»). Связи — `taiga_link` последними, когда у
   всех задействованных записей уже есть `#ref` (раздел «Блокировки»).
6. **Разбери результат.** Каждый вызов `taiga_bulk_create` возвращает
   `created` и `failed`. Разбери причины неудач и повтори запрос только с
   ними — не создавай всё заново.

## Формат историй

Каждый элемент принимает те же поля, что `taiga_userstory_create`. Заголовок —
формулировка результата, а не техническое задание; описание — рубрики
`## Описание` (польза первой фразой) и `## Критерии приёмки` (3–5 строк-правил
отдельными строками, без буллетов — как в `taiga-requirements`):

```json
{
  "subject": "Сброс пароля по email работает без поддержки",
  "description": "## Описание\nЧтобы поддержка перестала сбрасывать пароли руками.\n\n## Критерии приёмки\nПисьмо приходит в течение минуты.\nСсылка живёт сутки.\nПосле смены пароля старые сессии закрыты.",
  "tags": ["auth"]
}
```

Статусы, исполнителей и спринт (`sprint: "<название>"`) указывай человеческими
именами — резолв в ID происходит сам. Поле `sprint` есть только у user
stories; в элементе `resource: "task"`/`"issue"` такой элемент вернётся в
`failed` с понятной причиной, а не будет создан молча без него. Поле `points`
при создании не заполняй: оценка — отдельный разговор с человеком, его ведёт
`taiga-estimate`.

## Задачи под историями

Заводи задачи только по условию из раздела «История — слайс ценности» выше,
вторым проходом, после того как истории получили номера: `taiga_bulk_create`
с `resource: "task"`, где `user_story` — номер `#ref` созданной истории. У
каждой задачи — `role` (`front`/`back`/`ux`/`design`, ложится тегом, смена
роли снимает прежний тег). Описание задачи — рубрики `## Что сделать`,
`## Как проверить`; у задачи с `role: "back"` ещё `## Контракт` — что она
отдаёт и что принимает, до того как кто-то начнёт делать фронт параллельно.

Оценок у задач нет — вес работы записан поинтами роли у истории
(`taiga-model`), и `estimate` не передавай вовсе. Роль у задачи при этом
обязательна: по ней истории разбирают на части, раздают работу и считают
загрузку.

## Блокировки

Реальную зависимость — а не порядок, который просто удобен показывать —
ставь `taiga_link` после того, как у обеих сторон есть `#ref`: `{ "from":
<#ref блокирующей>, "to": <#ref заблокированной>, "type": "blocks" }`. Раньше
момента создания ссылаться не на что. Работает и для историй, и для задач;
`remove: true` снимает связь. Уже поставленные связи видны в
`taiga_userstory_get`/`taiga_task_get` с `fields: "full"` (поля `blocked_by`,
`blocks`). Зависимость, которую источник не называет явно, не придумывай —
как и критерии.

## Discovery и артефакты дизайна

Исследование, прототип, дизайн-макет — это тоже история, а не задача: у неё
есть проверяемый результат (вопрос закрыт, макет готов к реализации), просто
не пользовательский. Заводи её обычной историей с тегом `discovery` и теми же
рубриками, чтобы она была видна в бэклоге отдельно от фич. Сам макет,
скриншот, файл — вложением через `taiga_attachment_upload`, не пересказом в
описании и не ссылкой на внешний файл, которого не будет через полгода;
загрузка требует подтверждения — спрашивай и дожидайся согласия.

## Эпики

Если источник — документ и материал явно делится на крупные направления,
можно предложить завести эпики через `taiga_epic_create` с рубриками
`## Цель`, `## Границы`, `## Готово, когда` — но не по своей инициативе,
спроси. Привязывай истории к эпику полем `epic`, в том числе прямо в
`taiga_bulk_create` (`"epic": "<название эпика>"`) — без отдельного прохода
`taiga_userstory_update` после пакетной заливки. Поле `epic` в элементах
`resource: "task"`/`"issue"` не имеет смысла — вернётся в `failed` с понятной
причиной. Если источник сам — существующий эпик, его не пересоздавай:
разбери по разделу «Откуда берёшь вход» и привязывай новые истории тем же
полем `epic`.

## Чего не делать

Не выдумывай критерии приёмки и зависимости, которых нет в источнике — ни в
документе, ни в описании эпика или истории. Если раздел или формулировка
слишком расплывчаты, чтобы стать историей или задачей, скажи об этом и
запиши строкой в `## Открытые вопросы`, а не сочиняй.
