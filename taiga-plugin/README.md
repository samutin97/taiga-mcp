# Плагин Taiga для Claude Code

Персональный плагин Claude Code для [Taiga](https://www.taiga.io/): MCP-сервер
из 42 инструментов, 11 скиллов на типичные сценарии работы с трекером —
отчёты по спринту, груминг и здоровье бэклога, приоритизация, оценка,
триаж issue, тест-планы, перенос спеки в бэклог, ведение своих задач по ходу
кодинга, — субагент для отчётов и хуки, которые принудительно проверяют
голос текста перед записью, границу загрузки файлов и не пропускают
секреты в ответах наружу.

Подключение — по адресу инстанса, логину и паролю. Application token
и OAuth не поддерживаются: это осознанный выбор ради простоты настройки
персонального инструмента, а не недосмотр.

## Установка

Сервер уже собран: `server/dist/index.js` закоммичен в репозиторий, и именно
его запускает манифест плагина (`${CLAUDE_PLUGIN_ROOT}/server/dist/index.js`).
Пересобирать его самому нужно только если вы меняете исходники — см. раздел
«Разработка» ниже.

Штатный путь — через локальный маркетплейс, который лежит в корне
репозитория (`.claude-plugin/marketplace.json`, `name: taiga-local`):

```bash
claude plugin marketplace add <путь к репозиторию>
claude plugin install taiga@taiga-local
```

Обе команды неинтерактивны. Установка попросит заполнить четыре настройки
плагина (`userConfig` в `.claude-plugin/plugin.json`): адрес Taiga, логин,
пароль и проект по умолчанию (необязательно) — сразу в диалоге установки
или позже через `/plugin` → `taiga` → Configure. Пароль помечен
`sensitive: true` и хранится в защищённом хранилище Claude Code, а не в
файле репозитория.

Проверить: попросить Claude выполнить `taiga_whoami`. Успешный ответ
отдаёт имя пользователя и список доступных проектов с их slug'ами.

Настройки доходят до MCP-сервера тремя путями по очереди — первый
непустой побеждает (`server/src/config.ts`):

1. **`TAIGA_URL` / `TAIGA_USERNAME` / `TAIGA_PASSWORD` / `TAIGA_PROJECT`** —
   значения `userConfig`, которые манифест напрямую подставляет в
   `mcpServers.taiga.env` (`"TAIGA_PASSWORD": "${user_config.taiga_password}"`
   и так далее). Основной путь; на этой машине именно он доставил пароль
   при приёмке 2026-09-12.
2. **`CLAUDE_PLUGIN_OPTION_TAIGA_*`** — те же значения под именем, которое
   Claude Code экспортирует по умолчанию для любого плагина. Резервный
   путь на случай, если хост-процесс вырезает из окружения переменные
   с `PASSWORD` в имени раньше, чем манифест успевает их подставить.
3. **`${CLAUDE_PLUGIN_DATA}/config.json`** (`{url, username, password,
   project}`) — последний резерв: файл в каталоге данных плагина, который
   можно завести вручную или через скилл `taiga-setup`, если оба
   источника окружения пусты.

Запасной путь — без маркетплейса, вручную: подключить каталог
`taiga-plugin/` как плагин Claude Code и задать переменные `TAIGA_*`
напрямую в окружении MCP-сервера (источник 1 выше):

| Переменная | Обязательна | Значение |
|---|---|---|
| `TAIGA_URL` | да | Адрес инстанса без `/api/v1`, например `https://taiga.example.com` |
| `TAIGA_USERNAME` | да | Логин |
| `TAIGA_PASSWORD` | да | Пароль |
| `TAIGA_PROJECT` | нет | Проект по умолчанию (id или slug); любой инструмент может переопределить его параметром `project` |

Если что-то не подключилось, инструменты Taiga вернут читаемую ошибку
(неверный `TAIGA_URL`, отказ логина, отсутствующая переменная) — подробный
разбор типичных сообщений есть в скилле `taiga-setup`.

## Что внутри

**42 инструмента**, схема — **29 625 символов** (~7 406 токенов, считая
только `name` + `description` + `inputSchema` — то, что реально попадает
модели в промпт) при жёстком пределе 32 000 символов; полный `tools/list`
«на проводе» (с `annotations` и `_meta`) — 36 069 символов, за это никто
из бюджета не платит. Следит `server/test/budget.test.ts`.

CRUD-фабрика на пять действий (`list`, `get`, `create`, `update`, `delete`)
для каждого из шести ресурсов даёт 30 инструментов:

`userstory`, `task`, `issue`, `epic`, `sprint`, `wiki`.

Плюс 12 сквозных:

- `taiga_project_list`, `taiga_project_get`, `taiga_project_schema`
- `taiga_comment_list`, `taiga_comment_add`
- `taiga_search` — полнотекстовый поиск по историям, задачам, issue, эпикам и wiki
- `taiga_bulk_create` — пачка историй, задач или issue за один вызов
- `taiga_stats` — статистика проекта или спринта с бёрндауном
- `taiga_attachment_list`, `taiga_attachment_upload`, `taiga_attachment_download`
- `taiga_whoami`

### Скиллы

11 скиллов в `skills/`, каждый описывает, когда применяться, какими
инструментами пользоваться и что требует явного согласия пользователя;
каждый пишущий скилл первой строкой загружает `taiga-voice`.

| Скилл | Когда |
|---|---|
| `taiga-setup` | Первое подключение к Taiga, ошибки авторизации или соединения, вопрос о доступных проектах, настройка проекта (спринты, канбан, статусы) |
| `taiga-sprint-report` | Рассказать, как идут дела по спринту/проекту, сводка к стендапу, бёрндаун, скорость, что заблокировано |
| `taiga-backlog-grooming` | Разобрать бэклог: порядок в историях, дубли, заброшенное, привязка к эпикам/спринтам, сборка/разгрузка спринта |
| `taiga-backlog-health` | Проверить бэклог/спринт на типичные проблемы: перегруз, зависшие и заблокированные истории, истории без пользы, слишком крупные истории |
| `taiga-prioritize` | Расставить приоритеты, сравнить важность, MoSCoW, матрица влияние/усилия, RICE, WSJF |
| `taiga-estimate` | Оценить истории в поинтах, планирование покером, сверка оценок, слишком крупные истории для резки |
| `taiga-issue-triage` | Разобрать входящие issue/баги: приоритет, severity, ответственные, дубли, что чинить первым |
| `taiga-stories-from-spec` | Завести задачи по документу, спеке, заметкам со встречи; разложить фичу на истории и задачи |
| `taiga-test-plan` | Составить тест-план/тест-кейсы к истории, проверка перед приёмкой, зафиксировать дефекты |
| `taiga-worklog` | По ходу работы над кодом: найти свою задачу, сменить статус, комментарий о прогрессе, блокировка, закрытие |
| `taiga-voice` | Не вызывается напрямую (`user-invocable: false`) — фоновая проверка голоса перед любой записью в Taiga; см. раздел «Голос» |

### Агент

`agents/taiga-reporter.md` — субагент только для чтения (без единого
пишущего инструмента), модель `sonnet`. Вызывается проактивно для любого
отчёта, чтобы длинные выгрузки историй/задач не засоряли основной контекст:
он пишет сводки и числа, а списки и JSON — только в файлы в scratchpad.

### Хуки

`hooks/hooks.json`, все — тонкие обёртки над `scripts/`:

| Событие | На чём | Скрипт |
|---|---|---|
| `PreToolUse` | 12 пишущих инструментов (`*_create`, `*_update`, `comment_add`, `bulk_create`) | `voice-gate.mjs` — проверка голоса перед записью |
| `PreToolUse` | `taiga_attachment_upload` | `upload-boundary.mjs` — путь вне текущего каталога требует подтверждения |
| `PostToolUse` | все 42 инструмента | `secret-scan.mjs` — ищет в ответе Taiga похожее на токен/подписанный URL/JWT |

### Скрипты

`scripts/` — чистый Node без зависимостей, вызывается одинаково откуда
угодно (`node "<корень плагина>/scripts/<имя>.mjs"`):

- `voice-gate.mjs` + `lib/voice-rules.mjs` — хук и `--file` CLI для
  проверки голоса (используются и в скилле `taiga-voice`).
- `upload-boundary.mjs`, `secret-scan.mjs` — hook-скрипты из таблицы выше.
- `score.mjs` — RICE/WSJF-калькулятор для `taiga-prioritize`.
- `audit.mjs` — восемь правил здоровья бэклога для `taiga-backlog-health`.

### Режимы

- **`TAIGA_READ_ONLY=1`** — регистрирует только 21 читающий инструмент
  (все `*_list`, `*_get`, `whoami`, `project_*`, `comment_list`, `search`,
  `stats`, `attachment_list`, `attachment_download`); ничего пишущего в
  наборе нет. Пригодится для отчётных/read-only сессий.
- **`TAIGA_VOICE_GUARD=off|warn|block`** (по умолчанию `off`) — та же
  проверка голоса, что в хуке, но внутри самого сервера, на тех же полях
  и по тем же правилам `scripts/voice-rules.json`. `warn` дописывает
  найденное в ответ инструмента, ничего не блокируя. `block` отказывает
  на **любую** находку — hard или soft, без разницы — и возвращает
  `isError` с перечнем причин; это жёстче хука (который на soft-правилах
  спрашивает, а не отказывает), но других степеней у guard нет: модель
  получает отказ, редактирует текст и вызывает инструмент заново. Подробнее — раздел «Голос».

## Голос

Всё, что плагин пишет в Taiga, читается коллегами как написанное владельцем
аккаунта — от первого лица, без следов инструмента. Это не пожелание к
стилю в промпте, а два детерминированных слоя поверх одних и тех же правил
из `scripts/voice-rules.json` (общая библиотека `scripts/lib/voice-rules.mjs`,
ни хук, ни сервер правил не дублируют):

- **Хук** `voice-gate.mjs` (`PreToolUse` на 12 пишущих инструментах) —
  перехватывает вызов до записи в Taiga.
- **Серверный guard** `TAIGA_VOICE_GUARD=off|warn|block` — та же проверка
  внутри самого сервера; см. «Режимы» выше. Пригодится хосту без хуков.

Правила — два уровня:

- **hard** (`ai-authorship`, одно правило) — текст прямо выдаёт, что его
  написал инструмент («сгенерировано», «as an AI», «с помощью нейросети» и
  т.п.). Хук отвечает `deny` без права обжалования; guard в режиме `block`
  отказывает так же. Единственное правило, которое не спрашивает.
- **soft** (`ai-mention`, `heading-label`, `emoji`, `bureaucratese`,
  `as-a-user`, `bullet-wall`) — голое упоминание ИИ/ассистента/модели,
  рубрики-заголовки («Контекст:», «Задача:»), эмодзи, канцелярит,
  форумный шаблон «Как пользователь, я хочу…, чтобы…», стена из шести и
  более буллетов подряд. Хук отвечает `ask` — в интерактивной сессии
  пользователь либо подтверждает текст как есть, либо просит переписать
  (в неинтерактивной подтвердить некому, и вызов просто не проходит — так
  и работает `claude -p`, см. приёмку). Guard в режиме `block` не различает
  hard и soft: **любая** находка отказывает вызов.

Отредактировать правила — значит: (1) поправить `scripts/voice-rules.json`
(поля `pattern`/`flags`/`reason`); (2) `npm run build` — сервер собирает
правила в бандл на этапе сборки, guard в `TAIGA_VOICE_GUARD` читает их
только оттуда, поэтому на хосте без хуков сборка — единственный способ
применить правку; (3) `npm run gen:eval-regex` — пересобрать семь копий
regex-грейдера eval-сьюта из того же JSON; (4) `npm test`. Все команды —
из `server/`. Правила голоса живут только в `scripts/voice-rules.json`,
остальное — производное от него.

Положить свои образцы стиля — `skills/taiga-voice/samples.md`. Пока файл
пуст, действуют только общие правила из `voice.md`; несколько настоящих
текстов делают правила вторичными — модель подражает образцам в первую
очередь.

## Особенности

- **Имена вместо ID.** Статусы, приоритеты, severity, типы issue и
  исполнители указываются человеческими именами («In progress», «High»,
  «Иван Петров»); перевод в числовые ID Taiga (свои в каждом проекте) делает
  сервер. Если имя не резолвится, ошибка перечисляет допустимые значения.
- **Экономный вывод.** По умолчанию (`fields: "slim"`) возвращается срез
  из 8–10 полей вместо полного объекта Taiga (у user story это 53 поля).
  На девяти историях песочницы это ~87% сокращения объёма JSON. Есть и
  `fields: "full"`, и явный список нужных полей.
- **Эпики.** `taiga_userstory_create` и `taiga_userstory_update` принимают
  поле `epic` — тему (subject) эпика, к которому привязывается история;
  пустая строка в `epic` при обновлении отвязывает историю от всех эпиков.
  `taiga_bulk_create` тоже понимает `epic`, но только для user stories —
  для task и issue это поле возвращает ошибку по конкретному элементу,
  а не тихо игнорируется.
- **Пустая строка очищает поле.** У полей, которые Taiga хранит как
  обнуляемые (`sprint`, `assigned_to`, `due_date`, `epic`), пустая строка
  в `_update` означает «снять значение»: `sprint: ""` возвращает историю
  в бэклог, `assigned_to: ""` снимает исполнителя. Другого способа очистить
  поле нет — `null` схема инструментов не принимает.
- **Бэклог — это фильтр, не отдельный ресурс.** `taiga_userstory_list` без
  фильтров отдаёт вообще все истории проекта, включая уже взятые в спринт.
  Чтобы увидеть именно бэклог (истории, не привязанные ни к одному спринту),
  нужен параметр `in_backlog: true` — другого способа получить этот список
  нет.
- **Удаление под защитой.** Все `_delete` требуют `confirm: true`. Это защита
  от случайного вызова, а не замена согласию пользователя — скиллы
  предписывают спрашивать явно до вызова.
- **Токен обновляется сам.** Access-токен Taiga живёт сутки; на HTTP 401
  сервер один раз тихо перелогинивается и повторяет запрос.
- **Массовое создание ограничено.** `taiga_bulk_create` — не более 50
  элементов за вызов, каждый создаётся независимо: неудача одного не
  останавливает остальные, результат приходит по каждому элементу отдельно.
- **Порядок и совладельцы истории.** `taiga_userstory_update` принимает
  `backlog_order` (позиция в бэклоге, меньше — выше) и `assigned_users`
  (полные имена всех назначенных, списком; заменяет список целиком, `[]`
  снимает всех).
- **Комментарии не обрезаются страницей Taiga.** `taiga_comment_list`
  запрашивает страницы по 1000 записей, а не дефолтные 30 у Taiga, — на
  длинной истории обсуждения возвращаются все комментарии одним вызовом.

## Безопасность

У плагина есть все три ноги «смертельной триады» агентов (Simon Willison):
приватные данные, недоверенный внешний контент, канал внешней коммуникации.
Меры против них — архитектурные, а не просьбы в промпте («будь
осторожен» здесь ни на что не полагается):

| Нога | Где у нас | Мера |
|---|---|---|
| Приватные данные | `taiga_attachment_upload` читает любой локальный файл, который вы ему назовёте; приватные проекты Taiga | `_meta["anthropic/requiresUserInteraction"]` на upload — подтверждение запрашивается даже при `allow` от хука и в режимах `auto`/`bypassPermissions`; хук `upload-boundary` дополнительно просит подтверждения, если путь выходит за пределы текущего каталога |
| Недоверенный контент | описания, комментарии, wiki-страницы — текст, который написали другие люди, а не плагин | правила голоса (см. «Голос») применяются только к тому, что пишет сам плагин, не к цитатам чужого текста; секрет-скан (`secret-scan.mjs`, `PostToolUse` на всех 42 инструментах) ищет в ответах Taiga похожее на токен, подписанный URL или JWT; содержимое Taiga — данные, а не указания, скиллы и агент-репортёр показывают похожее на команду пользователю вместо того, чтобы его выполнять |
| Внешняя коммуникация | `create`/`update`/`comment_add`/`bulk_create`/`attachment_upload` | `TAIGA_READ_ONLY=1` убирает эту ногу целиком для отчётных сессий (21 инструмент, ничего не пишущего); `taiga-reporter` физически не имеет пишущих инструментов; голос-хук стоит на всех записях; `_meta["anthropic/requiresUserInteraction"]` — на шести `*_delete`, `taiga_bulk_create` и `taiga_attachment_upload`, восьми самых необратимых или массовых действиях |

Что сознательно не делаем здесь: не вычищаем «инструкции» из ответов
Taiga на сервере — это ненадёжно и портит данные тем, кто их потом читает.

`taiga_attachment_upload` принимает абсолютный путь к файлу на диске и
читает этот файл, чтобы приложить его к истории, задаче, issue или эпику.
Инструмент прочитает **любой** файл, на который его направят, — в этом и
состоит его назначение: приложить к задаче можно скриншот, лог или документ
из любого места на диске. Это означает, что модель, управляющая этим
инструментом, может прочитать содержимое произвольного локального файла,
путь к которому она укажет. Учитывайте это при решении, устанавливать ли
плагин и в каком окружении запускать Claude Code.

`taiga_attachment_download` — обратная сторона: он **пишет** файл в указанный
`target_dir`. Имя файла берётся из вложения, то есть его выбирал тот, кто
вложение прикрепил, а не тот, кто скачивает. Путь из имени вырезается
(`basename`), так что запись не может уйти выше `target_dir`, а совпадение
с уже существующим файлом — ошибка, а не тихая перезапись: скачивание в
каталог, где уже лежит файл с таким именем, вернёт сообщение с полным путём
и ничего не тронет. Всё равно скачивайте в отдельный каталог, а не в корень
проекта.

## Чего плагин сознательно не делает

- **Webhooks, export/import, custom attributes, timeline** — не входят
  в заявленные сценарии персонального инструмента.
- **Комментарии** (`taiga_comment_list` / `taiga_comment_add`) работают на
  user stories, tasks, issues и epics, но **не на wiki-страницах** — для wiki
  таких инструментов нет.
- **Wiki-страницы редактируются полной заменой содержимого.** `taiga_wiki_update`
  принимает новый Markdown целиком; добавления к существующему тексту
  (append), в отличие от `_update` у остальных ресурсов, нет.
- **Вложения ограничены 100 МБ** — это не собственное решение плагина,
  а предел, на котором сам gateway Taiga отбрасывает запрос.
- **Application tokens, OAuth, мультиаккаунтность.** Один логин, одна
  неявная сессия на процесс.

## Ядро и адаптеры

Плагин сейчас работает в Claude Code, но бо́льшая часть кода не знает об
этом хосте и переносима на другой (в перспективе — ChatGPT):

```
server/                  ЯДРО     MCP-сервер; createServer() не выбирает транспорт
scripts/                 ЯДРО     детерминированные проверки и расчёты, чистый Node
skills/*/reference.md    ЯДРО     методология, нейтральный markdown
skills/taiga-voice/*.md  ЯДРО     правила и примеры голоса (кроме SKILL.md)
skills/*/SKILL.md        АДАПТЕР  фронтматтер Claude + воркфлоу со ссылками на reference.md
hooks/                   АДАПТЕР  тонкие обёртки над scripts/
agents/                  АДАПТЕР  субагент Claude Code
evals/                   АДАПТЕР  раннер Claude; промпты и грейдеры переиспользуемы
.claude-plugin/          АДАПТЕР  манифест, userConfig
```

Правила переноса:

- `server/` и `scripts/` не импортируют Claude-специфичные пакеты и не
  знают про хуки; конфигурация сервера читается через `server/src/config.ts`
  (три источника — см. «Установка» выше). Добавить ещё один источник —
  одна функция там же.
- Проверка голоса — общая библиотека `scripts/lib/voice-rules.mjs` с
  двумя потребителями: хук и серверный `TAIGA_VOICE_GUARD`. У хоста без
  хуков (например, будущего ChatGPT-адаптера) `TAIGA_VOICE_GUARD=block` —
  единственный детерминированный замок.
- `reference.md` (в каждом скилле) и `voice.md`/`examples.md`/`samples.md`
  (в `taiga-voice`) не содержат фронтматтера и Claude-специфичных ссылок;
  их можно склеить в инструкцию Custom GPT / Project без правок.
- Из полей фронтматтера `SKILL.md`, переносимых по спецификации Agent
  Skills, используются только `name`, `description`, `allowed-tools`.
  **Единственное Claude-специфичное поле — `user-invocable: false` у
  `taiga-voice`**: вне Claude Code это неизвестное поле и ошибка, так что
  адаптер для другого хоста обязан вырезать эту одну строку перед
  переносом. `context`, `hooks`, `disable-model-invocation` не
  используются нигде.
- Скрипты вызываются одинаково отовсюду:
  `node "<корень плагина>/scripts/<имя>.mjs"`; в Claude Code корень —
  `${CLAUDE_PLUGIN_ROOT}`.

## Оценки

```bash
cd taiga-plugin
claude plugin eval . --case "positive-1" --runs 2 --max-cost-usd 10 --no-publish --trust-plugin -j 3 --threshold 0.8
claude plugin eval . --case "negative-1" --runs 2 --max-cost-usd 10 --no-publish --trust-plugin -j 3 --threshold 0.8
claude plugin eval . --case "?"          --runs 2 --max-cost-usd 10 --no-publish --trust-plugin -j 3 --threshold 0.8
```

`--case "?"` — единственный рабочий способ достать шесть голосовых кейсов
(`voice/1`…`voice/6`, однобуквенные имена листовых каталогов): `--case`
сравнивает только имя листового каталога кейса, а не полный путь, так что
`taiga-*` и `taiga-setup/*` не матчат ничего. Полный разбор селекторов,
устройства моков и отдельный прогон `holdout/` (не используется при
доводке скиллов, прогоняется один раз на приёмке) — в `evals/README.md`.

Дельты последнего прогона на приёмке (2026-09-12, полные таблицы —
`docs/2026-09-12-acceptance.md`): активация — 20/20 кейсов
(10 позитивных + 10 негативных) прошли; дельта «с плагином − без» — 1 на
большинстве позитивных кейсов и 0.33 у трёх скиллов с дополнительными
sibling-грейдерами (`taiga-backlog-grooming`, `taiga-backlog-health`,
`taiga-prioritize` — три скилла легко перепутать по формулировке запроса,
их позитивный кейс несёт «не сработал сосед»-грейдеры с `arm: both`, и
делит дельту втрое, не будучи регрессией), 0 на всех негативных; голос —
6/6 кейсов по большинству голосов судьи; holdout — 3/3 (`taiga-prioritize`,
`taiga-stories-from-spec`, голос).

## Разработка

Тесты идут против локального стенда Taiga — как его поднять и заполнить
тестовыми данными, написано в `../infra/README.md`.

Нужен **Node.js 20.11 или новее** (это же записано в `engines` в
`server/package.json`): собранный `dist/index.js` рассчитан на node20, а тесты
используют `import.meta.dirname`, появившийся в 20.11.

```bash
cd server
npm install            # только для разработки; конечному пользователю плагина не нужен
npm test                # vitest run (весь server/test) && node --test ../scripts/*.test.mjs
npm run typecheck
npm run build            # пересобрать dist/index.js
```

`npm test` — это два раннера одной командой: `vitest run` гоняет
TypeScript-тесты сервера (юнит и интеграционные — против локального
стенда), `node --test ../scripts/*.test.mjs` следом гоняет юнит-тесты
скриптов (`voice-gate`, `upload-boundary`, `secret-scan`, `score`,
`audit`, `hooks`) на чистых фикстурах, без сети и без зависимостей —
именно так `scripts/` и остаётся переносимым ядром (см. «Ядро и
адаптеры»). На приёмке 2026-09-12: `vitest` — 26 файлов / 202 теста,
`node --test` — 38 тестов, всё зелёное.

`server/test/budget.test.ts` следит, чтобы прод-фейсинговая часть схемы
инструментов (`name` + `description` + `inputSchema`) не превышала
32 000 символов, и что имя каждого инструмента соответствует
`taiga_[a-z_]+`. Падение этого теста — сигнал, что витрина разрослась и новую
функциональность надо оформлять скиллом, а не ещё одним инструментом.

`dist/index.js` собирается esbuild'ом в один файл со всеми зависимостями
и коммитится в репозиторий — именно поэтому плагину не нужен `npm install`
на машине, где его использует Claude Code.
